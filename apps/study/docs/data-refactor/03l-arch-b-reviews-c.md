# 架构师 B 评审架构师 C（DDD派）方案

> 评审立场：物化缓存派。在认同 DDD 方案的设计严谨性的同时，重点审查它在本地 PWA 场景下的必要性与落地风险。

---

## 总体判断

架构师 C 的方案在**设计严谨性**上是三个方案里最高的：域边界清晰、职责不重叠、EventBus 解耦优雅、未来接入后端自然。但这套方案是为"后端微服务"场景设计的思维框架，移植到一个**单用户本地 PWA** 上，引入的复杂度远超解决的问题。

结论：**方案设计优秀，但不适合当前阶段。核心疑问未解决，不建议采用。**

---

## 一、值得肯定的部分

### 1.1 域划分语义清晰

C 方案把四个域（学习、复习、计划、用户）的边界讲清楚了，比 A、B 方案更系统。这对团队对齐"谁该管什么"很有价值，即使不实施 DDD，这个域模型也可以作为代码组织的参考。

### 1.2 poem_queue 归属计划域的论据充分

C 方案对 poem_queue 为什么不该进学习域的论证（意图 ≠ 行为、生命周期不同、触发时机不同）比 B 方案更完整。B 方案只是说"应该独立存在"，C 方案给了具体的语义原因。我同意这个归属。

### 1.3 achievement_events 改为追加记录是改进

原来的 `poem_achievement_dates`（Record 结构）只存"首次解锁时间"，改为追加记录后可以保留完整历史，未来支持"撤销/重放"也有依据。这是一个低成本的改进，值得采纳，与是否实施 DDD 无关。

### 1.4 review_sessions 字段对比

C 方案的 review_sessions 比 A 方案少了 `intervalUsed` 和 `efBefore`（A 方案的讨论中已决定加这两个字段用于精确重建 SM-2）。C 方案只存 `levelBefore/levelAfter/intervalBefore/intervalAfter`，存的是结果而非输入参数。这两种设计各有侧重：

- A 方案的字段（efBefore + intervalUsed）：可以重放 SM-2 计算，验证 ef 是否被正确更新
- C 方案的字段（levelBefore/After + intervalBefore/After）：记录状态变化快照，可读性更高

C 方案的字段设计更直观，但无法从历史序列精确重建 ef——这是 A 方案的关键诉求。**建议合并：同时存 efBefore + intervalBefore/intervalAfter**，覆盖两个场景。

## 二、核心质疑：EventBus 在本地 PWA 的必要性

这是我对 C 方案最大的疑问，也是 C 方案自己在"疑问4"里承认的问题。

### 2.1 EventBus 解决了什么问题？

C 方案引入 EventBus 的目的是：**学习域写入 session 后，不直接调复习域，而是通过事件通知**，让复习域自己决定如何响应。

这在分布式系统或微服务里是标准做法，理由充分：各服务独立部署、独立扩缩容，必须通过消息队列解耦。

但在本地 PWA 里，"学习域"和"复习域"都是同一个 JS 进程里的对象，调用方式无非是：

```ts
// 方案C：间接调用
learningService.saveSession(...)
// → emit('learning.session_saved')
// → reviewDomain.on('learning.session_saved') → reviewService.initSchedule(...)

// 方案B：直接调用
async function handleReciteDone() {
  await saveRecitationSession(...)
  await initReviewScheduleIfNew(poemId, qScore)
}
```

两种写法的**运行时行为完全相同**，但 EventBus 版本多了：
- 一个额外的内存对象（EventBus 实例）
- 事件注册/注销管理（App 启动时要统一注册所有 handler）
- 事件处理失败后没有错误冒泡（fire-and-forget，调用方不知道复习域初始化是否成功）
- 调试链路变长（出了问题要追 emit → handler 的异步链路）

### 2.2 "解耦"在本地场景的代价

EventBus 解耦的好处是"写入方不依赖处理方"。但在本地单用户 PWA 里，这个好处几乎为零：

1. 没有"独立部署"需求——学习域和复习域永远在同一个 bundle 里
2. 没有"消费者动态增减"需求——成就检查永远在，不会在运行时动态挂载/卸载
3. 没有"背压控制"需求——数据量极小，不存在生产者速度超过消费者的场景

代价却是真实的：**一致性变弱**。

C 方案的疑问4（事件处理 fire-and-forget，`initSchedule` 失败时无补偿）在当前架构下是一个已知的弱点。直接调用版本（B 方案的 handleReciteDone）在同一函数里写多个 key，任何一步失败可以整体报错，调用方能感知到并决定是否重试。EventBus 版本做不到这一点。

**结论：EventBus 在本地 PWA 的必要性极低，但引入了不可忽视的一致性风险。**

## 三、与物化缓存方案的对比

### 3.1 数据层面的差异

C 方案的数据结构与 A 方案基本一致（均无 poem_states），差异主要在代码组织层面。从存储 key 看：

| Key | C 方案 | B 方案 |
|-----|-------|-------|
| recitation_sessions | 保留，append-only | 相同 |
| review_sessions | 保留，append-only | 相同 |
| review_schedules | 保留，复习域状态 | 合并进 poem_states |
| poem_states | 不存在 | 存在（物化缓存） |
| achievement_events | 新增（append-only） | 不存在（保留 poem_achievement_dates）|

C 方案在**数据层**上的选择更接近 A 方案（纯实时计算），而不是 B 方案。C 方案真正独特的贡献是**代码组织层**的域服务划分。

### 3.2 物化缓存与域服务不冲突

B 方案（poem_states）和 C 方案（EventBus + 域服务）是**正交的**：可以同时有"物化缓存的 poem_states"和"基于域服务的代码组织"，两者不互斥。

C 方案选择不要 poem_states，理由是"用 useMemo 在内存中解决"（这和 A 方案的立场一致）。但这意味着：
- 每次 App 冷启动，要加载 recitation_sessions + review_sessions 全量数据，在内存里计算所有诗的统计状态
- ProgressContext 或各页面的 useMemo 要维护整张"诗的状态 map"
- 后续增加统计指标，要在多处 useMemo 里同步修改

poem_states 解决的恰好是这个问题：把"当前状态"物化到一张表，读取和更新都有明确的写入点，不依赖"全量加载后的内存 map"。

**C 方案没有解释为什么拒绝 poem_states，只是延用了 A 方案的选择。**

### 3.3 ProgressContext 的问题 C 方案没有真正解决

C 方案疑问2承认 ProgressContext 的处理是两难：
- 保留：职责仍然混乱（应用层跨域聚合）
- 拆散：改动面大，短期风险高

这个问题在 B 方案里同样存在，差别在于：B 方案的 poem_states 让 ProgressContext 内部逻辑简化（直接读 poem_states，不需要跨表聚合），而 C 方案的 ProgressContext 需要跨学习域、复习域、用户域查询数据，更复杂而非更简单。

## 四、迁移成本评估

### 4.1 C 方案的迁移成本高于 A/B 方案

C 方案要求在数据重构的同时完成：
1. 建立 4 个域服务层（LearningService、ReviewService、PlanService、UserService）
2. 建立 EventBus 和所有事件 handler
3. 将所有现有的 Hook（useRecitation、useQueue、useAchievements）改为调用对应域服务
4. 将 ProgressContext 改为跨域聚合层

这是**架构重构 + 数据重构**同步进行，风险是 A/B 方案的两倍。A/B 方案只需要重构数据层，代码组织（Hook 结构）基本不变。

### 4.2 迁移失败的恢复路径更长

A/B 方案的迁移如果出问题，影响范围是"某个 Hook 读到了错误的数据"，定位和修复比较直接。C 方案的迁移如果出问题，可能是"事件 handler 注册时机不对导致某个域没有初始化"，或"某个域服务在 EventBus handler 里出错但调用方不知道"，调试链路更长。

### 4.3 C 方案的迁移友好性不如它声称的

C 方案说"迁移本身不受架构风格影响，复用 plan.md 的迁移方案"。这只在数据 key 的迁移层面成立。但消费方（所有读写这些 key 的代码）都要从现有 Hook 迁移到域服务，这部分改动量远大于 A/B 方案。

## 五、"未来接入后端"的论据质疑

C 方案反复提到 EventBus 的优势是"未来接入后端时只需替换 EventBus 实现"。

这个论据我有两个疑问：

**疑问1：接入后端时，EventBus 真的是扩展点吗？**

接入后端同步，核心问题是：
- 冲突解决（本地和服务器同时修改同一首诗的状态）
- 增量同步（只同步上次同步后的变化）
- 离线 → 在线时的合并策略

这些问题的答案都在**数据层**（append-only records 天然支持增量同步），而不在 EventBus 里。把本地事件路由到后端队列，处理的是"实时推送"场景，而不是"离线优先 PWA"的同步场景。换句话说，EventBus 的"后端扩展"是锦上添花，不是核心。

**疑问2：如果要接入后端，A/B 方案的迁移路径同样清晰**

A/B 方案的 append-only sessions 天然是事件日志，接入后端时同样可以遍历 sessions 增量推送。不需要 EventBus 预先埋点。

## 六、C 方案的疑问逐一回应

### 疑问1（重背已调度的诗，复习域如何响应）

这个问题 B 方案没有明确回答，但 B 方案的处理路径更简单：背诵和复习在同一个函数里处理，判断"是否是首次背"和"是否已有调度"可以在同一段代码里完成，不需要通过事件通知。

**我的观点：选项A（忽略）更合理**。SM-2 的设计前提是"有规律的复习"，用户主动重背不等于复习，不应该修改 ef/interval。如果用户重背且效果好（stars=3），可以在下次到期复习时得到体现。

### 疑问2（ProgressContext 保留还是拆散）

这个问题 A/B/C 三个方案都面对。我的看法和 C 方案一致：短期保留，内部逐步委托，接口不变。**但 B 方案的 poem_states 让"保留 ProgressContext"代价更小**——读取只需要 O(1) 读 poem_states，不需要跨多个域服务聚合。

### 疑问3（实时计算性能边界）

C 方案对500条以内的情况乐观，但对"批量导入历史数据"场景没有设计。这个场景在 B 方案里有明确答案：poem_states 坏了可以 rebuildPoemStates()，批量重建后正常使用。C 方案的"增量缓存"策略只是一句"建议"，没有具体方案。

### 疑问4（EventBus fire-and-forget 的一致性）

这是 C 方案设计的根本缺陷，C 方案自己也承认了。我的回应是：**在单用户本地 PWA 里，不值得为"解耦"付出"一致性无保证"的代价**。直接调用（B 方案的写法）更安全，也同样可测。

### 疑问5（计划域 streak_count 去掉后的激励）

这是产品决策，不是架构决策。A/B/C 三个方案都同样面对这个问题，与是否采用 DDD 无关。

## 七、综合评分

| 维度 | A 方案 | B 方案 | C 方案 |
|------|-------|-------|-------|
| 设计严谨性 | 中 | 中高 | 高 |
| 实施复杂度 | 低 | 中 | 高 |
| 迁移风险 | 中（SM-2 精度） | 低 | 高（架构+数据同步改） |
| 本地一致性保证 | 高（单一来源） | 高（原始记录优先） | 中（EventBus fire-and-forget）|
| 读性能 | 中（全量实时算） | 高（O(1)读缓存） | 中（同A）|
| 可测试性 | 中 | 中 | 高（域服务可独立测）|
| 后端扩展性 | 高（append-only 天然支持） | 高 | 高（EventBus 额外加成有限）|

## 八、我的建议

**不建议在当前阶段实施 C 方案的 DDD 架构层**，但建议**选择性采纳 C 方案的数据设计改进**：

1. **采纳**：achievement_events 改为 append-only 追加记录（低成本，改善历史可审计性）
2. **采纳**：poem_queue 归属计划域的语义定义（指导代码注释和文档，不需要新建域服务）
3. **不采纳**：EventBus 事件机制（本地 PWA 场景无必要，引入一致性风险）
4. **不采纳**：强制的 4 域服务层（可以作为未来目标，但当前阶段直接调用即可）
5. **不采纳**：放弃 poem_states 物化缓存（C 方案没有给出充分理由，B 方案的缓存方案在读性能和可调试性上有明确优势）

**最终，B 方案（物化缓存派）在当前阶段是更合适的落地方案**。C 方案描述的域边界和职责划分，可以作为代码注释、README 和函数命名的指导，而不必作为运行时架构强制实施。
